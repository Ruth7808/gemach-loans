# פרומפט לקלוד קוד — שלב ב׳: בקשות משיכה, אלגוריתם סיכון, ודשבורד
 
הקשר: המשך ישיר לשלב א׳ (מפקידים והפקדות כבר בנויים ועובדים, כולל טבלאות
WithdrawalRequest/Withdrawal שכבר קיימות בסכימה מהמיגרציה הקודמת — לא צריך
ליצור אותן מחדש). זה השלב המורכב — קח את הזמן על סעיף 2 (האלגוריתם), הוא
הלב של הפיצ'ר.
 
## עיקרון מנחה שחשוב להבין לפני שמתחילים
 
הבדיקה "האם יש מספיק כסף להחזיר למפקיד" היא **הרחבה סימטרית** של מנגנון
ה-FIFO שכבר קיים במערכת להקצאת תשלומים ללוואות (טבלת Allocation) — רק
הפוך: כאן "משבצים" כסף פנוי לבקשות משיכה במקום לשבץ תשלומים להתחייבויות.
 
## 1. עדכון סטטוס בקשת משיכה — מה מאוחסן ומה מחושב
 
**מאוחסן בטבלה** (סטטוס תהליכי בלבד): `פתוחה` / `שולמה_חלקית` / `שולמה` /
`בוטלה`.
 
**מחושב בזמן אמת בכל שליפה, לעולם לא מאוחסן**: `isReady` (תאריך יעד ≤
היום) ו-`isAtRisk` + `shortfall` (מהאלגוריתם למטה). **חשוב:** אם תשמור
"בסיכון" כעמודה היא תתיישן ברגע שמצב הקופה משתנה — אסור לשמור אותה.
 
## 2. אלגוריתם בדיקת סיכון — בנה כפונקציה משותפת אחת, לא ישירות ב-route
 
בנה פונקציה (למשל `calculateWithdrawalRisk(hypotheticalAvailableMoney?)`)
שתשמש גם את ה-API של בקשות משיכה, גם את הדשבורד, וגם את בדיקת יצירת
הלוואה (סעיף 5 למטה) — כדי לא לשכפל את הלוגיקה בשלושה מקומות.
 
**האלגוריתם:**
1. שלוף את כל בקשות המשיכה הפתוחות (`פתוחה`/`שולמה_חלקית`), ממוין לפי
   תאריך יעד עולה.
2. יתרת ריצה = כסף פנוי נוכחי (או `hypotheticalAvailableMoney` אם הועבר
   פרמטר — ראה סעיף 5).
3. לכל בקשה בתור, לפי סדר:
   - הוסף ליתרת הריצה רק את ה-Installments החדשים (שלא נספרו כבר בבקשה
     קודמת בלולאה) שתאריך היעד שלהם ≤ תאריך היעד של הבקשה הנוכחית.
   - הפחת מיתרת הריצה את (סכום הבקשה − שולם עד כה).
   - יתרת ריצה ≥ 0 → הבקשה מכוסה. יתרת ריצה < 0 → הבקשה בסיכון, `shortfall`
     = מינוס יתרת הריצה, וכל הבקשות הבאות בתור גם בסיכון.
4. החזר מערך של {requestId, isAtRisk, shortfall} לכל הבקשות שנבדקו.
 
**כתבי טסטים ידניים** (2-3 תרחישים עם כמה בקשות מתחרות ותאריכים שונים)
לפני שסומכים על הפונקציה הזו — היא הכי קריטית בכל הפיצ'ר.
 
## 3. API — בקשות משיכה ומשיכות
 
`/api/withdrawal-requests`:
- GET — כולל שדות מחושבים: תאריך יעד, שולם עד כה, נותר, `isReady`,
  `isAtRisk`, `shortfall`.
- GET/:id — פרטים.
- POST — **ולידציה חובה**: סכום מבוקש ≤ (Σהפקדות המפקיד − Σמשיכות שכבר
  שולמו לו − Σסכומי בקשות פתוחות אחרות שלו). תאריך יעד = תאריך בקשה +
  `withdrawal_notice_days` (מ-Setting), מחושב אוטומטית — **אל תיתן למשתמש
  לערוך את תאריך היעד ידנית**.
- PUT/:id — עדכון (מותר רק אם הסטטוס עדיין `פתוחה`, ולידציה מחדש מול
  היתרה הפנויה; **אל תאפס את תאריך היעד גם אם עורכים את הסכום** — היעד
  כבר הובטח למפקיד).
- POST /:id/cancel — משנה סטטוס ל`בוטלה`, "משחרר" את הסכום כך שהוא לא
  ייספר יותר בולידציה של בקשות עתידיות ולא באלגוריתם הסיכון.
- POST /:id/pay — **בטרנזקציה אחת** (בדיוק כמו רישום Payment הקיים):
  יוצר שורת Withdrawal, מעדכן שולם-עד-כה על הבקשה, ומעדכן סטטוס
  (`שולמה_חלקית` אם חלקי, `שולמה` אם הושלם). תומך בתשלום בכמה פעימות.
  **מותר לשלם לפני תאריך היעד** — תאריך היעד הוא תקרה, לא רצפה, אין
  לחסום תשלום מוקדם.
 
`/api/withdrawals`:
- GET (סינון לפי מפקיד/בקשה) — לצפייה בלבד. **אל תיצור endpoint ישיר
  ל-POST משיכות** — משיכות רגילות נוצרות רק דרך `/pay`, כדי לשמור על
  התהליך התקין. (חריג: אם רוצים לתמוך במשיכה בלי בקשה מוקדמת בכלל —
  `withdrawal_request_id` null — אפשר endpoint נפרד מסומן בבירור כ"משיכה
  חריגה ללא התראה מוקדמת", ראה עקרונות ב-README/CLAUDE.md אם קיים כזה
  מהתכנון; אם לא ברור, השאירי את זה כ-TODO מסומן ואל תבני שקט.)
 
## 4. מסכים
 
1. **כרטיס מפקיד** — הוסף עכשיו אזור בקשות משיכה: רשימה עם תגיות סטטוס
   (פתוחה / מוכנה לתשלום / **בסיכון** / שולמה / בוטלה), כפתור "בקשת משיכה
   חדשה".
 
2. **רשימת בקשות משיכה** — מסך חדש ברמת הניווט הראשי, מקביל לרשימת
   הלוואות. סינון לפי סטטוס, מיון לפי תאריך יעד. **צבע לסיכון: כתום/צהוב,
   לא אדום** — אדום כבר תפוס ל"הלוואה באיחור" במערכת, ושני הבעיות שונות
   במהות; שימוש באותו צבע יבלבל.
 
3. **דשבורד** — הרחב את ה-API והתצוגה עם: סה"כ יתרת מפקידים, מספר/סכום
   בקשות משיכה פתוחות, וכרטיס אזהרה "בקשות משיכה בסיכון" (שם מפקיד, חוסר,
   תאריך יעד) — **רק אם יש בפועל בקשות בסיכון; אל תציג כרטיס עם "0 בסיכון"
   כשאין צורך**.
 
## 5. שינוי במערכת הקיימת — בדיקה בעת יצירת הלוואה חדשה
 
זה שינוי ב-endpoint/מסך יצירת ההלוואה ה**קיימים**, לא CRUD חדש. לפני
שמירת הלוואה חדשה:
 
1. חשב `כסף_פנוי_היפותטי` = כסף פנוי נוכחי − סכום ההלוואה החדשה.
2. אם שלילי → אזהרה חמורה (אדום): "אין מספיק כסף פנוי" + סכום החוסר.
3. הרץ את `calculateWithdrawalRisk()` פעמיים — עם כסף פנוי נוכחי ועם
   `כסף_פנוי_היפותטי` — והשווה תוצאות. אם בקשה כלשהי עוברת מ"לא בסיכון"
   ל"בסיכון" → אזהרה (כתום): אילו מפקידים/בקשות ייפגעו ובכמה.
4. אם שתי הבדיקות נקיות — ההלוואה נשמרת רגיל, בלי הפרעה.
 
**UX: אזהרה עם אישור (confirm), לא חסימה מוחלטת** — עקבי עם העיקרון שהמערכת
"רושמת ומזכירה, לא אוכפת". בעל הגמ"ח מקבל את ההחלטה הסופית.
 
## 6. בדיקות לפני שמסיימים
 
- תרחיש עם 2-3 בקשות משיכה בתאריכי יעד שונים ותשלומים צפויים ביניהם —
  ודא שהאלגוריתם מסמן בדיוק את הבקשות הנכונות כבסיכון.
- ביטול בקשה בסיכון — ודא שהבקשות אחריה בתור "משתחררות" בהתאם.
- יצירת הלוואה חדשה שדוחפת בקשה קיימת לסיכון — ודא שהאזהרה מופיעה ושאפשר
  לאשר ולהמשיך.
- תשלום חלקי על בקשת משיכה, ואז תשלום נוסף שמשלים אותה.
